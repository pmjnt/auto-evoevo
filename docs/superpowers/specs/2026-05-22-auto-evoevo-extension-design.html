1. Goal & non-goals

Goal

  • Auto-click ADD TO MEMORY and SHOW MORE on https://evoevo.ai/feed.
  • Replace Rabby on this site: extension exposes window.ethereum (EIP-1193).
  • Validate every eth_sendTransaction with the existing guard rules and sign locally with an encrypted-at-rest key.
  • Pause (never sign) when guards fail; surface the reason in the popup.

Non-goals

  • Chrome Web Store distribution.
  • Other wallets (WalletConnect, hardware, MetaMask Snap).
  • Chains other than 0G.
  • Reverse-engineering the EvoEvo contract ABI. data is treated as opaque bytes gated by function-selector whitelist.

2. Current runner vs new extension

Today — Playwright/CDP runner existing

  • Node process + Playwright launches a dedicated Chrome profile.
  • Reads the Rabby popup with innerText and parses it with regex.
  • Guard fields (origin, chain, contract, fee) are inferred from text.
  • Stops on any non-approve outcome; user resumes by restarting the process.
  • Friction: separate profile setup, Node toolchain, fragile to Rabby UI changes.

Proposal — MV3 extension new

  • Installs into the user's normal Chrome profile.
  • Extension is the wallet: reads to, data, value, gas directly.
  • Guard works on a typed object — no text parsing, no Rabby dependency.
  • Pause/resume from the popup; key stays in-memory only.
  • Tradeoff: extension must implement a minimal EIP-1193 provider; user disables Rabby on this site.

3. Architecture

Four execution contexts, each with one responsibility, communicating only through typed messages.

EvoEvo tab (page) Background (service worker) UI surfaces External RPC / chain

Why this split

  • inpage must run in main world to be visible as window.ethereum. Main world has no chrome.*.
  • content runs in isolated world: holds DOM automation + bridges messages.
  • background is the only place the private key lives (in-memory after unlock).
  • popup/options talk to background through the same typed message API.

4. Data flow — one ADD TO MEMORY click

Pipeline design choices

  • actionFingerprint = function selector (first 4 bytes of data). Config adds allowedFunctionSelectors: string[]; guard rejects on mismatch.
  • Guard adds: data.length >= 4, value === 0n, selector ∈ whitelist.
  • Nonce + gas fetched by background, never trusted from the page.
  • Origin verified via sender.tab.url — content-supplied origin is ignored.
  • Rejection code 4001 to EvoEvo (no leak of guard reasons). Detailed reason stays in extension log.
  • v1 only signs eth_sendTransaction. Other write methods (personal_sign, eth_sign, eth_signTypedData_*, wallet_*) return code 4200 (unsupported).

Idempotency

  • data-auto-evoevo-attempted-id marker prevents re-clicking the same button (carried over from controller.ts:5).
  • inflight entry keyed by (nonce, keccak(data)). On SW wake, missing receipt ⇒ poll instead of re-sign.

9. Testing strategy

Unit

  • guard — port + new checks
  • crypto — round-trip, wrong password, IV random
  • wallet — locked/unlock, idle-lock fake timers
  • rpc — retry/backoff, nonce-too-low
  • messages — zod schema accept/reject

Integration

  • pipeline — fakes for wallet/rpc/guard; verify gating
  • automation — DOM fixture; pause on 4001; skip marked buttons
  • Service-worker wake replay with inflight set

Manual smoke

  • Load unpacked at chrome://extensions → no errors
  • Import burner key on 0G testnet → unlock
  • Dry-run ON: walk feed, all dry_run
  • Dry-run OFF, 1 card: tx appears on explorer with expected to, fee ≤ cap
  • Force cap too low → pause with reason

10. Open questions to confirm during implementation

  • 0G chain id (mainnet vs testnet) and RPC URL — copy from the user's existing Rabby network config rather than guess.
  • Whether 0G supports EIP-1559. If yes use maxFeePerGas/maxPriorityFeePerGas; otherwise legacy gasPrice.
  • Whether EvoEvo dispatches EIP-6963. If not, README instructs disabling Rabby on this site.
  • The exact function selector(s) EvoEvo calls. Capture from a real successful tx (block explorer "Input Data") and seed allowedFunctionSelectors.

11. Acceptance criteria

  • Extension loads in Chrome MV3 without errors.
  • Dry-run ON: walks feed end-to-end, JSONL log compatible with SessionLogger shape, extended with txHash and additional status values.
  • Dry-run OFF + one whitelisted selector: every approved tx is signed and broadcast to 0G; non-approve outcomes pause and never sign.
  • Guard reuses src/guard.ts logic; behaviorally equivalent on the same WalletRequest inputs.
  • Private key never reaches any context other than background/wallet.ts; vault at rest is AES-GCM-encrypted.
  • All unit and integration tests pass under vitest run.
